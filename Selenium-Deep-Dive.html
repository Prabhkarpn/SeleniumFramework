1. How the Web Actually Works (Foundation)

Before learning Selenium, every trainee should understand what's happening when they open a website. This 10-minute foundation prevents 80% of confusion later.

1.1 The big picture: client and server

YOUR LAPTOP (client) SOMEWHERE ON THE INTERNET (server) +-------------------+ +------------------------+ | Chrome browser | ---HTTP req---> | Web server (Apache, | | | | nginx, Node, ...) | | | <--HTML/CSS/JS--| | +-------------------+ +------------------------+

When you type https://orangehrmlive.com and press Enter:

  1. Chrome opens a network connection to the server.
  2. It sends an HTTP request: "GET / HTTP/1.1, Host: orangehrmlive.com".
  3. The server responds with HTML text (and references to CSS/JS/images).
  4. Chrome parses the HTML into the DOM (a tree of elements).
  5. Chrome downloads CSS & JS, applies styles, runs scripts.
  6. Chrome paints the result on screen.
Real-life analogy Opening a webpage is like ordering a flat-pack from IKEA:
  • You order (URL) — the truck delivers parts (HTML).
  • The instruction manual is the CSS (how it should look) and JS (interactive bits).
  • You assemble it (browser builds the DOM and renders it).
  • It takes a few seconds. During those seconds, things appear gradually.
That last point is critical: the page is not "ready" the moment get(url) returns. Selenium tests need to wait for things to be ready.

1.2 What is HTML, really?

HTML is just text. The browser reads this text and builds an in-memory tree. Here's a tiny page:

<!DOCTYPE html>
<html>
  <head><title>Login</title></head>
  <body>
    <h1>Welcome</h1>
    <form id="loginForm">
      <input name="username" placeholder="Username" />
      <input name="password" type="password" />
      <button type="submit">Login</button>
    </form>
  </body>
</html>

The browser builds this DOM tree:

html | +-- head | +-- title ("Login") | +-- body +-- h1 ("Welcome") +-- form id="loginForm" +-- input name="username" +-- input name="password" +-- button type="submit" ("Login")

Each rectangle in the tree is a node. Selenium's locators are queries against this tree: "find me the input node whose name attribute is username".

1.3 Static HTML vs Dynamic JS-driven pages

Static page (old-school)

Server sends complete HTML. By the time you see it, all elements exist. Easy to automate.

Examples: a simple Wikipedia article, a documentation site.

Dynamic page (modern SPA)

Server sends mostly empty HTML + a big JS bundle. JS then fetches data and builds the elements after the page loads.

Examples: Gmail, Facebook, Jira, OrangeHRM. Most real-world apps.

Why this matters for Selenium On a dynamic page, when driver.get(url) returns, the page is mostly empty. The login form doesn't exist yet — JS is still building it. If you try to find username immediately, you'll get NoSuchElementException. This is why we have waits.

1.4 The browser's rendering pipeline

1. Receive HTML text from server 2. Parse HTML -> build DOM tree 3. Parse CSS -> build CSSOM (style tree) 4. Combine -> Render Tree (DOM + styles) 5. Layout -> compute positions/sizes 6. Paint -> draw pixels on screen 7. Run JS -> may modify DOM, restart from step 4

Key insight: JavaScript can change the DOM at any time. So an element that exists at second 0 may be gone at second 2 (replaced by JS), then reappear at second 3. This is why we get StaleElementReferenceException.

1.5 Network: HTTP requests in DevTools

Open DevTools → Network tab. Reload a page. You'll see dozens of requests:

  • Document — the initial HTML.
  • Stylesheet — the CSS files.
  • Script — the JS files.
  • XHR / Fetch — AJAX calls (the dynamic data).
  • Image / Font — assets.
Pro test tip Many flaky tests fail because a background XHR hasn't finished. Open the Network tab, find the slow XHR, and in your test wait for the resulting UI element rather than a fixed time.

1.6 What you should do as a beginner (10-minute exercise)

  1. Press F12 right now.
  2. Visit any website. Click the Elements tab. See the DOM tree.
  3. Click the Network tab, reload, watch requests fly.
  4. Click the Console tab. Type document.title. The browser prints the title.
  5. Type document.querySelector('input'). The browser finds the first input.

That last command — document.querySelector(...) — is exactly what Selenium calls under the hood when you write driver.findElement(By.cssSelector(...)). Selenium doesn't use magic; it uses the browser's own native APIs.

2. Selenium WebDriver Architecture (How It Really Works)

To write reliable tests, you must understand what happens when you call driver.findElement(...). Spoiler: it's an HTTP request, not a function call.

2.1 The full picture

+------------------+ HTTP/JSON +------------------+ Native API +-------------+ | Your Java test | -- POST /session ---> | Browser Driver | -- click(elem) --> | Browser | | (selenium-java | | (chromedriver, | | process | | client lib) | <-- response -------- | geckodriver) | <-- result ------- | (Chrome) | +------------------+ +------------------+ +-------------+ ^ ^ ^ You write this Separate executable that Normal browser, controlled in Java implements W3C WebDriver via "automation port" Protocol over HTTP the driver opens

2.2 What happens, step by step

// Your code:
WebDriver driver = new ChromeDriver();
driver.get("https://orangehrm.com");
driver.findElement(By.name("username")).sendKeys("Admin");

Behind the scenes:

  1. new ChromeDriver() — Java starts the chromedriver executable on a random local port (e.g. 9515).
  2. Chromedriver, in turn, launches Chrome with a special flag: --remote-debugging-port=....
  3. Chrome is now controllable. Chromedriver returns a session ID to Java.
  4. driver.get(url) → Java sends POST http://localhost:9515/session/<id>/url with body {"url":"https://..."}.
  5. Chromedriver translates that into a Chrome DevTools Protocol command: navigate to URL.
  6. Chrome navigates, returns OK.
  7. findElement(By.name("username")) → Java sends POST /session/<id>/element with body {"using":"css selector","value":"[name='username']"}.
  8. Chromedriver runs document.querySelector("[name='username']") in the page.
  9. Chrome returns the matching DOM element. Chromedriver gives it a unique element ID and returns that to Java.
  10. .sendKeys("Admin") → Java sends POST /session/<id>/element/<el-id>/value. Driver dispatches keyboard events to that element.
Why this matters Every Selenium command is a network round-trip. A test with 200 commands has 200×~5ms = ~1s of pure overhead. It's also why parallel tests need ThreadLocal drivers — each thread needs its own session ID.

2.3 The W3C WebDriver Protocol

Selenium 4 conforms to the official W3C WebDriver standard. That means:

  • HTTP/JSON commands are standardized across all browser drivers.
  • You write the same Java code for Chrome, Firefox, Edge — only the driver differs.
  • The protocol is versioned; old "JSON Wire Protocol" (Selenium 3) is gone.

The W3C endpoints follow a consistent pattern: POST/GET/DELETE /session/{id}/path. Examples:

Selenium methodHTTP call
new ChromeDriver()POST /session
driver.get(url)POST /session/{id}/url
driver.getTitle()GET /session/{id}/title
driver.findElement(By.id("x"))POST /session/{id}/element
element.click()POST /session/{id}/element/{el-id}/click
driver.quit()DELETE /session/{id}

2.4 Selenium Manager (the modern win)

Pre-Selenium 4.6, you had to manually download chromedriver.exe and ensure its version matched your Chrome. Pain. Selenium 4.6+ ships Selenium Manager: when you create new ChromeDriver(), it:

  1. Detects your Chrome version.
  2. Downloads the matching chromedriver to a cache.
  3. Starts it transparently.

Your repo uses selenium-java 4.28.1 — you get this for free.

2.5 Capabilities & Options (browser configuration)

Before launching the driver, you can configure how the browser starts:

ChromeOptions options = new ChromeOptions();
options.addArguments("--start-maximized");
options.addArguments("--incognito");
options.addArguments("--headless=new");              // run without UI
options.addArguments("--disable-notifications");
options.addArguments("--lang=en-US");
options.setAcceptInsecureCerts(true);              // for self-signed SSL

WebDriver driver = new ChromeDriver(options);

Headless mode is critical for CI — servers don't have a display. Always test headless once locally before pushing to CI.

2.6 Key takeaways

  • WebDriver is a client-server system, even on your laptop.
  • Every command costs a network round-trip — minimize commands when you can.
  • Different threads must use different sessions → ThreadLocal.
  • The driver executable must match the browser version, not Selenium's version.
  • W3C standardization makes cross-browser tests realistic.
Interview question Q: How does Selenium WebDriver communicate with the browser?
Selenium uses the W3C WebDriver Protocol over HTTP. The Selenium client library serializes commands to JSON, sends them via HTTP to a browser-specific driver executable (chromedriver, geckodriver, etc.), which uses the browser's native automation API to execute and returns the result.

A variable is a named container that stores one value. Every variable in Java has a type declared upfront.

Worked Example — Why type matters
int a = 5;
int b = 2;
System.out.println(a / b);    // prints 2  (integer division!)

double c = 5;
double d = 2;
System.out.println(c / d);    // prints 2.5

3.4 Loops — deep dive

3.4.1 The classical for loop

for (int i = 0; i < 10; i++) {
    System.out.println(i);
}

Three parts: init; condition; increment. The condition is checked before each iteration. i++ is shorthand for i = i + 1.

3.4.2 Enhanced for-each

List<String> users = List.of("alice", "bob", "carol");
for (String u : users) {
    System.out.println(u);
}

Read it as: "for each String u in users". Cleaner when you don't need the index.

3.4.3 while & do-while

// while: check first, then run
int i = 0;
while (i < 5) {
    System.out.println(i);
    i++;
}

// do-while: run first, then check (always runs at least once)
int j = 10;
do {
    System.out.println(j);
    j++;
} while (j < 5);   // prints 10, then exits

3.4.4 break & continue

for (int i = 0; i < 10; i++) {
    if (i == 5) break;        // stop the loop entirely
    if (i % 2 == 0) continue;   // skip rest, go to next iteration
    System.out.println(i);
}
// prints: 1, 3
Practice

Problem: Given a list of links found on a page, print each link's text, but stop as soon as you encounter a link with text "Logout".

Answer:

List<WebElement> links = driver.findElements(By.tagName("a"));
for (WebElement link : links) {

3.7 Object-oriented programming — deeply

3.7.1 Class & object

public class User {
    // Fields (state)
    private String username;
    private String password;
    private boolean isAdmin;

    // Constructor
    public User(String username, String password) {
        this.username = username;
        this.password = password;
        this.isAdmin  = false;
    }

    // Methods (behavior)
    public String getUsername() { return username; }
    public void setAdmin(boolean v) { this.isAdmin = v; }
}

// Use it:
User u1 = new User("alice", "pass1");
User u2 = new User("bob",   "pass2");
u1.setAdmin(true);
System.out.println(u1.getUsername());

3.7.2 Encapsulation

Make fields private, expose them via getters/setters. Why? So you control how they're set:

private int age;

public void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("Age cannot be negative");
    this.age = age;
}

3.7.3 Inheritance

public class Animal {
    protected String name;
    public void eat() { System.out.println(name + " eats."); }
}

public class Dog extends Animal {
    public Dog(String n) { this.name = n; }
    public void bark() { System.out.println("Woof!"); }
}

// Use:
Dog d = new Dog("Rex");
d.eat();    // inherited from Animal
d.bark();   // own method

In Selenium frameworks, BaseClass contains driver setup; every test class extends it to inherit that setup. That's pure inheritance.

3.7.4 Polymorphism

One reference type, many possible runtime types:

WebDriver driver;                      // the interface (the abstract type)
driver = new ChromeDriver();         // runtime type is ChromeDriver
driver = new FirefoxDriver();        // or FirefoxDriver
driver.get("https://...");          // works on both. Same call, different impl.

This is why your BaseClass can read browser=chrome from config and produce a WebDriver reference that the rest of the framework uses without caring which browser.

3.7.5 Abstraction

Hide complexity behind a clean interface. The WebDriver interface defines methods like get, findElement, quit — the user calls them, the implementation handles the messy details.

public interface Vehicle {
    void start();
    void stop();
}

public class Car implements Vehicle {
    public void start() { /* engine logic */ }
    public void stop()  { /* braking logic */ }
}

3.8 Exception handling — the right way

Java exceptions form a hierarchy:

Throwable +-- Error (JVM-level. Don't catch.) +-- Exception +-- IOException, SQLException, ... (CHECKED - must declare/catch) +-- RuntimeException +-- NullPointerException +-- IllegalArgumentException +-- NoSuchElementException <-- Selenium +-- StaleElementReferenceException <-- Selenium +-- TimeoutException <-- Selenium

try / catch / finally

try {
    driver.findElement(By.id("submit")).click();
} catch (NoSuchElementException e) {
    logger.error("Submit button missing on page");
} catch (Exception e) {
    logger.error("Unexpected: " + e.getMessage());
} finally {
    // always runs (success or failure). Useful for cleanup.
    driver.quit();
}

try-with-resources (auto-cleanup)

try (FileInputStream fis = new FileInputStream("data.xlsx");
     Workbook wb = new XSSFWorkbook(fis)) {
    // use fis and wb. They auto-close at end of try block.
}

throw / throws

public void login(String u, String p) throws InvalidCredentialsException {
    if (!isValid(u, p)) {
        throw new InvalidCredentialsException("Bad creds for: " + u);
    }
}

3.9 Static vs instance

public class Counter {
    private int count;            // instance: each Counter has its own
    private static int total;     // static: shared across ALL Counters

    public void increment() {
        count++;
        total++;
    }
}

Counter a = new Counter(); a.increment(); a.increment();
Counter b = new Counter(); b.increment();
// a.count = 2, b.count = 1, Counter.total = 3

Static methods are called via the class: Math.sqrt(9), Integer.parseInt("42"). Your BaseClass.getDriver() is static so any class can call it.

3.10 The 5 Java mistakes that hurt Selenium tests most

  1. Using == with Strings. Use .equals().
  2. Calling methods on null. Always check (or use findElements().size() instead of findElement).
  3. Forgetting throws on a method that throws checked exceptions (e.g., InterruptedException from Thread.sleep).
  4. Hardcoding indexes in arrays when the page might change. Use locators that uniquely identify, not "the 3rd input".
  5. Sharing a non-thread-safe object across threads (e.g., raw WebDriver instead of ThreadLocal<WebDriver>).
Interview question Q: Difference between abstract class and interface?
Interface = contract only (no fields originally; from Java 8 default methods are allowed). Abstract class = a class with some abstract methods + maybe concrete methods + state. Use interface for "this can do X" (capability). Use abstract class for "this is a kind of Y" (relation).

4.2 Attributes — in detail

Attributes are key=value pairs inside the opening tag. They store metadata used by the browser, JS, and your locators.

<input
   id="emailInput"
   name="email"
   type="email"
   class="form-control required"
   placeholder="Enter email"
   value="alice@x.com"
   data-test-id="login-email"
   maxlength="50"
   required
   autofocus />
  • id: should be unique on the page. Best locator.
  • name: groups form fields together when submitted. Often unique.
  • class: visual styling. Can have multiple values separated by spaces (class="btn primary large").
  • type: kind of input (text, password, email, checkbox, radio, file, submit…).
  • data-*: custom attributes, often added specifically for tests (data-test-id).
  • Boolean attributes (required, disabled, checked): just present, no value.

4.3 The DOM — "live" vs "static"

The DOM is live: any change made by JavaScript (or the user) is reflected. Selenium's findElement queries the live DOM each time. Once you have a WebElement, it points to a specific node. If JS replaces that node, your reference becomes stale.

Worked example — StaleElementReferenceException
// Page A: a button that, when clicked, replaces itself with a new "Submitted" button

WebElement btn = driver.findElement(By.id("submit"));
btn.click();                      // triggers JS that replaces the button
btn.click();                      // FAIL: btn now points to a removed DOM node
                                  // => StaleElementReferenceException

// Fix: re-find the element
driver.findElement(By.id("submit")).click();
driver.findElement(By.id("submit")).click();   // fresh reference each time

4.4 Forms in detail (because they show up everywhere)

<form action="/login" method="post">
    <label for="un">Username</label>
    <input id="un" name="username" type="text">

    <label for="pw">Password</label>
    <input id="pw" name="password" type="password">

Important details:

  • button type="submit" submits the form. type="button" is just a clickable button (no form submit).
  • Pressing Enter inside a text input also submits the form.
  • You can use element.submit() in Selenium as an alternative to clicking the submit button.

4.5 Tables — the test pattern

<table id="employeesTable">
  <thead>
    <tr><th>ID</th><th>Name</th><th>Action</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Alice</td><td><a>Edit</a></td></tr>
    <tr><td>2</td><td>Bob</td><td><a>Edit</a></td></tr>
  </tbody>
</table>

// Click "Edit" for "Bob"
driver.findElement(By.xpath(
    "//table[@id='employeesTable']//tr[td[text()='Bob']]//a[text()='Edit']"
)).click();

// Read all names
List<WebElement> nameCells = driver.findElements(
    By.xpath("//table[@id='employeesTable']//tbody/tr/td[2]"));
for (WebElement c : nameCells) {
    System.out.println(c.getText());
}

This is the most-asked Selenium interview question: "How do you find Edit button for Bob in a table?" The trick is XPath chaining: tr[td[text()='Bob']] selects the row that contains a cell with text "Bob".

4.7 Shadow DOM (advanced, but coming up more)

Some modern web components (like custom Material/Stencil components) hide their internals inside a shadow DOM. Normal CSS/XPath cannot pierce it. You need:

WebElement host = driver.findElement(By.cssSelector("my-custom-button"));
SearchContext shadow = host.getShadowRoot();
WebElement btn = shadow.findElement(By.cssSelector("button.primary"));
btn.click();
Interview question Q: How would you handle elements inside Shadow DOM?
Selenium 4 added getShadowRoot() on WebElement. You first locate the host element, then call getShadowRoot() to get a SearchContext, then find children inside. Note: only CSS selectors work inside the shadow root, not XPath.

5. Locator Strategy Workshop

Most flaky tests aren't caused by Selenium — they're caused by bad locators. This workshop teaches you to write locators that survive UI changes.

5.1 The locator quality scale

QualityExampleSurvives
S-tier (best)By.id("loginBtn")Almost any change. Stable, unique, semantic.
S-tierBy.cssSelector("[data-test-id='loginBtn']")Custom test attributes — ideal in modern apps.
A-tierBy.name("username")Form refactors, style changes.
B-tierBy.xpath("//button[text()='Login']")Style changes; breaks if text changes.
C-tierBy.cssSelector("button.btn.btn-primary.large")Many class lists are styling-only and change with redesigns.
F-tier (worst)By.xpath("/html/body/div[2]/div[1]/form/button")Breaks at the slightest DOM change. Avoid.

5.2 The 8 Selenium locators — with detail

5.2.1 By.id — the gold standard

// HTML: <button id="loginBtn">Login</button>
driver.findElement(By.id("loginBtn")).click();

Pros: fastest, unique by HTML spec, semantic.
Cons: many modern apps don't add IDs (or add auto-generated ones like mat-input-127).

Auto-generated IDs Frameworks like Angular Material can produce IDs like mat-input-127. The number changes on every render, breaking your locator. Don't use these. Either use contains in XPath/CSS to match the prefix, or ask devs to add stable data-test-id.

5.2.2 By.name

// HTML: <input name="username" />
driver.findElement(By.name("username")).sendKeys("Admin");

Often used by your repo's LoginPage.java. The name attribute is the form field's identity at the HTTP level — reasonably stable.

5.2.3 By.className — tricky

Limitation: only works with a SINGLE class name. className("btn primary") — fails (compound class).

// HTML: <button class="btn primary large">OK</button>
driver.findElement(By.className("btn"));         // works (matches any of the 3)
driver.findElement(By.className("btn primary")); // FAILS

// Use CSS instead for compound:
driver.findElement(By.cssSelector(".btn.primary"));   // dot for each class

5.2.4 By.tagName

Mostly used to count or iterate.

List<WebElement> allInputs = driver.findElements(By.tagName("input"));
List<WebElement> allLinks  = driver.findElements(By.tagName("a"));
List<WebElement> allRows   = driver.findElements(By.tagName("tr"));

5.2.5 By.linkText & By.partialLinkText

Only for <a> tags.

// HTML: <a href="/logout">Logout</a>
driver.findElement(By.linkText("Logout")).click();          // exact match
driver.findElement(By.partialLinkText("Log")).click();      // matches "Login","Logout","Logo Suite"

5.2.6 By.cssSelector — powerful, fast

See full reference in chapter 7 below.

5.2.7 By.xpath — most flexible

See full reference in chapter 6 below.

5.3 Combining locators — findElement within WebElement

You can scope a search to a parent element. Useful for table rows, cards, list items.

5.4 The relative-locator API (Selenium 4)

Find elements based on their visual position relative to other elements. Useful when nothing else identifies them uniquely.

import static org.openqa.selenium.support.locators.RelativeLocator.with;

WebElement label = driver.findElement(By.tagName("label"));
WebElement input = driver.findElement(with(By.tagName("input")).below(label));

WebElement total = driver.findElement(By.id("total"));
WebElement submit = driver.findElement(with(By.tagName("button")).near(total));

Available helpers: above, below, toLeftOf, toRightOf, near, straightAbove, etc.

5.5 The "right" locator decision tree

1. Does the element have a stable id? YES -> By.id("...") <-- DONE NO -> step 2 2. Is there a stable data-test-* attribute? YES -> By.cssSelector("[data-test-id='...']") <-- DONE NO -> step 3 3. Is there a unique name attribute (input/select/textarea)? YES -> By.name("...") <-- DONE NO -> step 4 4. Can a CSS selector with class/attribute uniquely identify it? YES -> By.cssSelector("...") <-- DONE NO -> step 5 5. Use XPath with text() or axes (parent/sibling/ancestor) By.xpath("//label[text()='Email']/following-sibling::input")

5.7 Common locator anti-patterns (don't do these)

  • Locators copied from DevTools: "Copy XPath" produces absolute paths. Always rewrite by hand.
  • Generic selectors: By.tagName("input") in findElement — will return the first input even if you wanted the 5th.

XPath is a query language for navigating XML/HTML trees. Once you understand it, you can locate any element on any page.

6.1 The XPath formula (memorize)

Interview question Q: How do you write XPath to find a parent element from a child?
Use the parent:: or ancestor:: axis. Example: //input[@id='email']/parent::div finds the div that directly wraps the email input. ancestor::form walks up to the nearest form.

8. Synchronization Mastery (Waits in Depth)

If you remember nothing else from this guide, remember this: 90% of flaky Selenium tests are timing problems. Master waits and your tests become rock-solid.

8.1 Why pages aren't "ready" instantly

A modern web app does this when you load a URL:

  1. Browser receives HTML → ~50ms.
  2. Browser parses HTML, downloads CSS/JS → ~200ms.
  3. JS framework (React/Angular/Vue) bootstraps → ~300ms.
  4. JS calls the backend API for data → ~500ms.
  5. JS renders elements based on the data → ~100ms.
  6. Animations finish → ~300ms.

So the login form might appear ~1.5 seconds after driver.get() returns. If you click immediately, you fail.

8.2 The 4 wait strategies (in order of preference)

Strategy 1: Don't wait at all (when possible)

If the page is fully static, no wait needed. Rare in modern apps.

Strategy 2: Implicit Wait

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
  • Set ONCE per session.
  • Applies to all findElement calls.
  • Polls the DOM every ~500ms until the element is present.
  • Only checks "present in DOM" — not visible, not clickable.

Works for static-ish pages. Falls short on dynamic UIs (element is in DOM but invisible behind a spinner).

Strategy 3: Explicit Wait (the recommended default)

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

WebElement el = wait.until(
    ExpectedConditions.elementToBeClickable(By.id("login")));
el.click();
  • Targeted: wait for THIS specific condition on THIS specific element.
  • Polls every ~500ms by default.
  • Throws TimeoutException if the condition isn't met within timeout.
  • Many conditions available: present, visible, clickable, text-equals, frame-available, etc.

Strategy 4: Fluent Wait (advanced control)

Wait<WebDriver> wait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(30))
    .pollingEvery(Duration.ofMillis(250))
    .ignoring(NoSuchElementException.class)
    .ignoring(StaleElementReferenceException.class);

WebElement el = wait.until(d -> d.findElement(By.id("result")));
  • Custom polling interval (faster than default).
  • Multiple ignored exception types.
  • Custom condition via lambda.

    By.cssSelector(".loading-spinner")));

8.5 The "wait for page fully loaded" recipe

public void waitForPageLoad() {
    WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(30));
    wait.until(d -> ((JavascriptExecutor) d)
        .executeScript("return document.readyState")
        .equals("complete"));
}

This is exactly what your ActionDriver.waitForPageLoad() does.

8.6 Custom condition with lambda (when built-ins don't fit)

// Wait until a list has at least 5 items AND first one says "ready"
wait.until(d -> {
    List<WebElement> items = d.findElements(By.cssSelector(".list-item"));
    return items.size() >= 5
        && items.get(0).getText().contains("ready");
});

8.7 The implicit + explicit wait gotcha

If you set BOTH:

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(5));

// What happens?  Could take up to 10s + 5s = 15s in worst case.
// Or only 5s. Behavior is documented but inconsistent in practice.
Recommendation Don't mix. Either set implicit to 0 (no implicit wait at all) and rely fully on explicit waits, or use only implicit. Industry standard: explicit-only.

8.8 Page-load timeout vs script timeout

// Maximum time for driver.get() to wait before throwing TimeoutException
driver.manage().timeouts().pageLoadTimeout(Duration.ofSeconds(60));

// Maximum time for executeAsyncScript()
driver.manage().timeouts().scriptTimeout(Duration.ofSeconds(30));

8.9 Wait debugging tips

  • If a wait fails: turn on logging in the action driver and print the locator. You'll see what was missing.
  • Capture a screenshot when wait fails — you'll see if the page even loaded.
  • Check Network tab in DevTools while a manual repro is happening. Slow XHR? Large image?
  • Use numberOfElementsToBeMoreThan with the result list to wait for "page is populated".

8.10 Real example from your framework

// In ActionDriver.java (simplified)
public void click(By by) {
    try {
        wait.until(ExpectedConditions.elementToBeClickable(by));
        applyBorder(by, "green");
        driver.findElement(by).click();
        logger.info("Clicked: " + by);
    } catch (TimeoutException e) {
        applyBorder(by, "red");
        logger.error("Element not clickable: " + by);
        throw e;
    }
}

Because this wait is INSIDE the click helper, every click in your framework auto-waits. You never have to write wait.until(...) in tests.

Interview question Q: A test passes locally but fails on CI — how do you debug?
Most common cause: timing. CI machines are slower, network is slower, no display = sometimes different rendering. Steps: (1) Take screenshot on failure. (2) Increase explicit wait timeouts. (3) Wait for spinners explicitly. (4) Run headed locally + headless in CI to compare. (5) Check if test depends on window size (CI default is small). (6) Add waits for AJAX-driven UI populations.

        this.actionDriver = BaseClass.getActionDriver();
    }

    // One method per business action
    public void login(String u, String p) {
        actionDriver.enterText(userField, u);
        actionDriver.enterText(passField, p);
        actionDriver.click(loginBtn);
    }

    public String getErrorMessage() {
        return actionDriver.getText(errorMsg);
    }

    public boolean isErrorMessageDisplayed() {
        return actionDriver.isDisplayed(errorMsg);
    }
}

Why this is better: every actionDriver.enterText / click / getText internally waits, logs, screenshots-on-failure. The page class focuses on the business meaning, not the mechanics.

Make page methods return the next page. Tests read like English:

9.6 Component pattern (huge time-saver)

If your app has reusable widgets (a date picker, a complex dropdown, a table), make each its own class. Pages compose components.

public class EmployeeTable {
    private ActionDriver actionDriver;
    private By rowByName(String name) {
        return By.xpath("//tr[td[normalize-space()='" + name + "']]");
    }
    private By editBtnInRow = By.xpath(".//button[@title='Edit']");

    public EmployeeTable(WebDriver driver) { ... }

    public void editEmployee(String name) {
        WebElement row = driver.findElement(rowByName(name));
        row.findElement(editBtnInRow).click();
    }
}

public class AdminPage extends BasePage {
    public EmployeeTable getEmployeeTable() {
        return new EmployeeTable(driver);
    }
}

9.7 Things to AVOID in page classes

  • Assertions — pages should expose state, tests should assert. (One exception: tiny pre-conditions like "is on this page" can be in pages.)
  • Test data — never hardcode "Admin", "admin123" inside a page class. Tests pass them in.
  • Sleeps — if a page method needs a sleep, fix the wait inside actionDriver.
  • Public locators — keep By objects private. Expose only behavior.
  • Driver passed all the way down — better to use the framework's BaseClass.getDriver() static accessor.

9.8 Quick checklist for a "great" page class

  • One class per logical page or component
  • Locators are private final By
  • Methods describe business actions ("login", "search", "addEmployee")
  • No findElement / sendKeys in tests — only page-method calls
  • No assertions inside the page (except pre-conditions)
  • Returns next page object when navigating
  • Uses the action-driver layer for all interaction
Interview question Q: Should page methods return WebElements or page objects?
Page methods should expose behavior, not raw elements. They return a Page Object (the next one if navigation, the same one otherwise) or a primitive (String, boolean) when reading state. Returning WebElements leaks implementation and tempts test code to call findElement/click directly — defeating POM.

10.8 RetryAnalyzer — full implementation

public class RetryAnalyzer implements IRetryAnalyzer {
    private static final int MAX_RETRIES = 2;
    private int attempt = 0;

    @Override
    public boolean retry(ITestResult result) {
        if (attempt < MAX_RETRIES) {
            attempt++;
            logger.warn("Retrying " + result.getName() + " attempt " + attempt);
            return true;
        }
        return false;
    }
}

// Apply to a single test:
@Test(retryAnalyzer = RetryAnalyzer.class)

// Apply to ALL tests via IAnnotationTransformer (cleaner):
public class RetryListener implements IAnnotationTransformer {
    public void transform(ITestAnnotation annotation, ...) {
        annotation.setRetryAnalyzer(RetryAnalyzer.class);
    }
}

10.11 Common TestNG mistakes

  • Forgetting sa.assertAll() on a SoftAssert → failures vanish.
  • Hard-coding browser inside test → can't run cross-browser. Use parameters.
  • Sharing state between tests via static fields → tests aren't independent.
  • Putting login inside every @Test → slow. Put in @BeforeMethod if all tests need it (or use API/cookie shortcut).
  • Setting parallel="methods" without ThreadLocal<WebDriver> → tests crash.
Interview question Q: How do priority and dependsOnMethods differ?
priority just orders test execution — it doesn't enforce success. If priority-1 fails, priority-2 still runs. dependsOnMethods creates an actual dependency: if the dependency fails, the dependent test is skipped (not failed). Use dependsOn sparingly — tests should be independent.

11. Top 25 Selenium Errors & How to Fix Them

Save this chapter for the day a test fails at 11pm. Each entry: the error, the cause, the fix.

11.1 NoSuchElementException

Cause: Selenium couldn't find the element matching your locator.

Fixes:

  1. Test the locator in DevTools (Ctrl+F in Elements panel). 0 matches? Bad locator.
  2. Element might be inside an iframe. Switch first: driver.switchTo().frame(...).
  3. Page might not have loaded yet. Add explicit wait.
  4. Element might be in a Shadow DOM — use getShadowRoot().

11.2 StaleElementReferenceException

Cause: The DOM element your WebElement points to was removed or replaced (usually by JS re-render).

Fixes:

  1. Re-find the element right before using it: driver.findElement(by).click() instead of caching.
  2. Use FluentWait with .ignoring(StaleElementReferenceException.class).
  3. Inside loops over findElements results, refresh the list after each action that mutates the DOM.

11.3 ElementClickInterceptedException

Cause: Another element (modal, banner, sticky header) is on top of the target.

Fixes:

  1. Wait for the overlay to disappear: wait.until(invisibilityOfElementLocated(By.css(".overlay"))).
  2. Scroll the element into view: js.executeScript("arguments[0].scrollIntoView(true);", el).
  3. Click via JS as a workaround: js.executeScript("arguments[0].click();", el).
  4. Dismiss the cookie banner / popup explicitly.

11.4 ElementNotInteractableException

Cause: Element is in DOM but not visible / not enabled / not in viewport.

Fixes:

  1. Use elementToBeClickable condition.
  2. Scroll into view.
  3. Some hidden form fields can be set via JS instead.

11.5 TimeoutException

Cause: Wait condition wasn't met within timeout.

Fixes:

  1. Check the locator (most common cause).
  2. Increase the timeout.
  3. Verify the page actually reaches the expected state (manual repro).
  4. Capture screenshot at the moment of timeout.

11.6 SessionNotCreatedException ("This version of ChromeDriver only supports…")

Cause: Chromedriver version doesn't match your installed Chrome.

Fix: Use Selenium 4.6+ (you do). Selenium Manager auto-fetches matching driver. Alternatively, update to latest selenium-java.

11.7 InvalidSelectorException

Cause: Bad XPath/CSS syntax (unmatched brackets, bad quotes).

Fix: Test the selector in DevTools Ctrl+F first. Always.

11.8 WebDriverException ("chrome not reachable")

Cause: Chrome process crashed or didn't start. Common in headless CI without enough resources.

Fixes:

  1. Add --no-sandbox and --disable-dev-shm-usage options on Linux CI.
  2. Increase Docker container memory.
  3. Restart the test pipeline.

11.9 NullPointerException on driver

Cause: driver is null. Almost always: forgot @BeforeMethod or test class doesn't extend BaseClass, OR ThreadLocal returned null in another thread.

Fix: Verify class extends BaseClass; verify @BeforeMethod sets up driver; verify ThreadLocal stores per thread.

11.10 NoSuchWindowException

Cause: Trying to switch to a window/tab that's already closed.

Fix: Track getWindowHandle() immediately after opening, switch using fresh getWindowHandles().

11.11 NoSuchFrameException

Cause: Frame index/name/element doesn't exist or you're already inside a different frame.

Fix: Call driver.switchTo().defaultContent() first to reset, then switch in.

11.12 UnexpectedAlertPresentException

Cause: A JS alert popped up but you didn't handle it; subsequent commands fail.

Fix: Add driver.switchTo().alert().accept() or set UnexpectedAlertBehaviour in capabilities.

11.13 Test passes locally, fails in CI

Common causes:

  1. Different window size in CI (default headless is 800×600 → some elements are off-screen).
  2. CI is slower → need longer waits.
  3. Animations not disabled headless.
  4. Cookies/cached state different.

Fixes:

options.addArguments("--window-size=1920,1080");
options.addArguments("--no-sandbox");
options.addArguments("--disable-dev-shm-usage");
options.addArguments("--disable-gpu");

11.14 sendKeys not typing

Causes: hidden input, masked input, custom JS handler not picking up.

Fix: Try actions.click(el).sendKeys(text).perform(), or set value via JS: js.executeScript("arguments[0].value=arguments[1];", el, "abc"); remember to dispatch input event afterwards.

11.15 Click not registered

Element is reachable but the click does nothing. Often happens with overly-quick clicks before JS handlers attach.

Fix: Wait for clickable; or use actions.moveToElement(el).pause(200).click().perform(); or click via JS.

11.16 Dropdown not selectable with Select class

Cause: It's not a real <select> — it's a fancy div-based dropdown.

Fix: Click to open, click the matching option element.

11.17 Test starts fast, slows down over runs

Cause: chromedriver processes leaking. Common when quit() isn't called.

Fix: Always call driver.quit() in @AfterMethod, even on failure (use finally or @AfterMethod(alwaysRun = true)).

11.18 InterruptedException not handled

Cause: Thread.sleep throws checked exception.

Fix: Wrap in try/catch or declare throws. Better: don't use Thread.sleep.

11.19 IFrame element invisible

Cause: Element is inside an iframe; you're in the main frame.

Fix: driver.switchTo().frame("frameName") first.

11.20 Element with display:none returns isDisplayed() = false even after JS shows it

Cause: Cached WebElement — the JS change happened after you got the reference.

Fix: Re-find the element after the JS action.

11.21 File upload doesn't work

Cause: The "upload" element is not a real <input type="file">.

Fixes:

  1. If real input: driver.findElement(uploadInput).sendKeys("/full/path/file.pdf").
  2. If hidden file input behind a fancy button: still send-keys to the input directly.
  3. If OS-level dialog: use Robot class or AutoIT (last resort).

11.22 ConnectionRefused on chromedriver

Cause: chromedriver crashed or port conflict.

Fix: Restart your IDE; check that no zombie chromedriver.exe is running.

11.23 ScreenshotException ("Could not take screenshot")

Cause: Page navigation in progress, alert open, or browser already closed.

Fix: Take screenshots before quit(), dismiss alerts first, wrap in try-catch.

11.24 Tests run in wrong order

Cause: Forgot priority or relying on alphabetic order which changed.

Fix: Don't depend on order. Each test should be independent. If sequencing is essential, use dependsOnMethods.

11.25 ExtentReport is empty

Cause: Forgot extent.flush(). Or the listener isn't registered. Or the test crashed before onFinish.

Fix: Call flush() in @AfterSuite or onFinish of the listener. Verify <listeners> in testng.xml.

General debugging recipe
  1. Read the FULL stack trace, not just the top line.
  2. Check the locator in DevTools.
  3. Take a screenshot at the failure moment.
  4. Try a manual repro at the same speed.
  5. Add a wait if timing-related.
  6. If still stuck, run with extra Chrome flags: --enable-logging --v=1.

Step 6: ActionDriver wrapper layer

public class ActionDriver {
    private WebDriver driver;
    private WebDriverWait wait;
    private static final Logger log = LogManager.getLogger(ActionDriver.class);

    public ActionDriver(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(20));
    }

    public void click(By by) {
        wait.until(ExpectedConditions.elementToBeClickable(by));
        driver.findElement(by).click();
        log.info("Clicked: " + by);
    }

    public void enterText(By by, String value) {
        wait.until(ExpectedConditions.visibilityOfElementLocated(by));
        WebElement el = driver.findElement(by);
        el.clear();
        el.sendKeys(value);
        log.info("Typed into " + by + ": " + value);
    }

    public String getText(By by) {
        wait.until(ExpectedConditions.visibilityOfElementLocated(by));
        return driver.findElement(by).getText();
    }

    public boolean isDisplayed(By by) {
        try {
            return wait.until(ExpectedConditions.visibilityOfElementLocated(by)).isDisplayed();
        } catch (TimeoutException e) {
            return false;
        }
    }
}
